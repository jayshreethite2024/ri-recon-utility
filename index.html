01 — The Problem

A critical control gap at billion-dollar scale.

Every production cycle, someone had to answer: did the reinsurance engine apply the treaty rules correctly? The answer required 2 days of manual Excel work — every month.

Context
Global Finance Transformation

A large global insurer replacing disparate homegrown reinsurance systems with a unified, automated, globally standardized solution. Accuracy at every handoff point was non-negotiable.

The Gap
Manual recon on millions of transactions

Reconciliation of actual vs. expected ceded amounts required per-policy interpretation of treaty attachment criteria — in Excel — taking 2 full working days per monthly cycle.

Cascade Effect
BAU offloading to QA teams

Volume and complexity meant BAU analysts could not keep up. Recon work was regularly handed to the QA team — misallocating technical resource to operational manual work.

Scale
Millions of transactions. Billions in impact.

The reinsurance engine processed transactions in the millions per run, covering billions in financial impact. Manual recon at this scale was a critical control gap with no automated backstop.

04 — The Iteration Story

Three versions. One insight.

Technical correctness is not product success. A tool that works perfectly but cannot be used by its intended users has failed its purpose.

V1
SQL + Database
Automate Excel recon

Faster and more accurate than Excel. But required uploading data to a database first — time-consuming, with inconsistent file format support. Computation on large datasets was slow. Required direct DB access and SQL knowledge to run.

What broke Data uploads to DB were time-consuming; file format sanitization was difficult; computation on large datasets was slow.
V2
PySpark Script
Handle scale, drop DB

Eliminated the database dependency entirely. Processed millions of transactions efficiently — no upload delays, no format issues. Technically the strongest version. But PySpark environment setup and command-line execution made it inaccessible for BAU users.

What broke PySpark environment setup was a barrier; command-line execution was too technical for BAU users to run independently.
V3
Streamlit + Pandas
Full BAU self-sufficiency

Browser-based. File upload. Configurable parameters on screen. Click to run. Summary displayed immediately. Zero technical prerequisites for any user.

Result BAU adopted independently from day one. Now expanding firm-wide.

“The problem to solve was no longer recon accuracy — that was solved in V1. The unsolved problem was making accurate recon accessible to the people who needed to run it.”

The pivot insight that drove V3
The requirements document told me what the tool needed to do. The users told me what the tool needed to be.
05 — Key Product Decisions

Seven decisions. Each with a reason.

Every decision below reflects a genuine tradeoff — where the PM thinking lives, not just in the output.

DECISION 01
SQL → PySpark → Streamlit

Each version solved the previous version's primary failure. Streamlit was not the first choice — it was the right choice after two iterations revealed that the interface, not the logic, was the adoption barrier.

DECISION 02
Treaty report as single source of truth

Expected cession calculated directly from the treaty report — not hardcoded logic. The utility stays accurate as treaty terms change, with zero code updates required per cycle.

DECISION 03
Surface error & retention analysis

Early versions only flagged amount mismatches. Stakeholder demos revealed BAU needed to know why transactions went to error or retention — output expanded based on observed behavior.

DECISION 04
Single file for international & domestic

BAU was manually separating files by transaction type before running recon. After demo feedback, the utility was redesigned to handle both in one file — eliminating that manual step entirely.

DECISION 05
Configurable parameters on screen

Cycle-specific values surfaced as interface inputs rather than hardcoded. BAU adjusts parameters per cycle without any developer involvement — genuine operational self-sufficiency.

DECISION 06
Two-layer output: summary on screen, detail in file

Observed in demos: every BAU analyst's first action after a run was to look for overall status. A summary on screen answered that question immediately. Detailed drill-down remained in the downloadable output for investigation. The design matched how users actually consumed results — not how the system produced them.

07 — PM Learnings

What this taught me about product thinking.

1
The user's constraint is part of the product requirement

V1 and V2 were technically correct — but the user's ability to operate the tool is as much a requirement as the tool's logic. Usability is not a layer on top of functionality. Every requirement has two dimensions: what the product does, and who can do it without help.

2
The real problem is rarely the stated problem

The stated problem was: recon is slow and inaccurate. V1 solved both. But adoption failed because the real problem was that recon required technical resource for an operational BAU task. Keep asking why until the root cause is clear.

3
Users show you what they need — they rarely tell you

Single file handling, configurable parameters, summary on screen — none were in any requirements document. All emerged from watching BAU analysts interact with the tool in demo sessions. Structured observation is more valuable than open-ended feedback.

4
Iteration is not failure — premature handoff is

Each version answered a question the previous one couldn't. The failure was handing V2 to BAU before V3's question had been asked. Before releasing to intended users, ask: can this person use this without help? If no, it's not ready — regardless of technical correctness.

5
Organic adoption is the most honest product metric

The utility was built for one project. Other reinsurance projects adopted it without a mandate. That organic spread — users recommending it without being asked — is the strongest validation signal the product received. Everything else can be manufactured. Organic spread cannot.
